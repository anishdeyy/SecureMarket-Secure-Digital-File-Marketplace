PART A — HIDE SHA-256 AND INTERNAL CRYPTOGRAPHIC DETAILS

============================================================



CURRENT PROBLEM:



The product detail page currently exposes technical security implementation details directly to buyers and sellers.



Examples currently visible:



- SHA-256 Verified

- Cryptographic Hash

- SHA-256 Digest

- Cryptographic File Authenticity

- Integrity Seal

- HMAC-Protected

- Live Server-Side Re-hash Audit

- Copy Digest

- Re-hash File Now



The full SHA-256 digest is also displayed in the UI.



THIS IS NOT DESIRED.



SHA-256 is an INTERNAL BACKEND SECURITY/INTEGRITY MECHANISM.



It must NOT be exposed to normal buyers or sellers.



============================================================

A1. SHA-256 MUST REMAIN IN THE BACKEND

============================================================



DO NOT remove SHA-256 functionality.



Continue using SHA-256 internally for:



- exact duplicate detection

- file integrity verification

- upload validation

- backend audit

- file fingerprinting

- integrity checks

- duplicate-content protection



But do NOT display the actual hash to:



- buyer

- seller

- public marketplace visitor



The SHA-256 value must remain internal.



============================================================

A2. REMOVE FROM PUBLIC / BUYER / SELLER UI

============================================================



Remove all visible occurrences of:



- SHA-256 Digest

- SHA-256 Hash

- Cryptographic Hash

- Full hash string

- Copy Digest

- Re-hash File Now

- Cryptographic File Authenticity

- HMAC-Protected

- HMAC seal

- Internal cryptographic implementation wording

- Internal storage/security implementation details



from:



- public product details

- buyer product page

- seller product page

- seller dashboard

- buyer dashboard

- marketplace cards

- home page

- download page

- purchase success page



Do NOT expose internal hash values through normal frontend API responses either.



If the frontend receives the complete SHA-256 hash but simply hides it with CSS, that is NOT sufficient.



DO NOT SEND THE HASH TO THE PUBLIC CLIENT AT ALL unless an authenticated admin/security endpoint explicitly requires it.



Security-sensitive backend data should not be returned unnecessarily.

PART B — IMPLEMENT COMPLETE VERIFIED BUYER REVIEW SYSTEM

============================================================



CURRENT PROBLEM:



The product page currently shows:



"Reviews (0)"



and:



"No reviews yet"



but even after successfully purchasing the product, the buyer cannot submit a review.



THIS MUST BE FIXED.



A buyer who has actually purchased the product must be able to submit a review.



The review must be:



- saved in PostgreSQL

- associated with the buyer

- associated with the product

- associated with the verified purchase/order

- visible to other users

- counted in the review total

- included in the average rating

- shown on the product page

- prevented from duplicate review submission unless editing is explicitly supported



============================================================

B1. VERIFIED PURCHASE REQUIREMENT

============================================================



Only a user with a successful completed purchase can review a product.



Backend rule:



User must have:



order.status == PAID



and:



order contains product



Only then:



can_review = true



A user who has NOT purchased the product must NOT be able to create a review.



This must be enforced on the backend.



Do NOT rely only on hiding the review button on the frontend.



============================================================

============================================================

Create or update:

Recommended:

verified_purchase = true



============================================================

B3. UNIQUE REVIEW RULE

============================================================



By default:



ONE REVIEW PER PURCHASED PRODUCT PER USER.



Add a database-level unique constraint such as:



unique(user_id, product_id)



OR if your business logic supports multiple orders:



unique(user_id, product_id, order_id)



For this project, prefer:



unique(user_id, product_id)



This prevents duplicate review spam.



If the buyer already reviewed the product:



show:



"You already reviewed this product."



and allow:



[Edit Review]



rather than creating another review.

============================================================



Create/verify these APIs.

Returns:



reviews

average_rating

review_count



POST:



POST /api/products/{product_id}/reviews



Request:



{

  "rating": 5,

  "comment": "Excellent resource."

}



Backend must:



1. Authenticate user.

2. Verify product exists.

3. Verify successful purchase.

4. Verify order contains product.

5. Verify user owns that order.

6. Check user has not already reviewed.

7. Validate rating.

8. Validate comment.

9. Create review.

10. Return saved review.
